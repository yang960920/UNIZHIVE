# Discord session and guild authorization policy

The live OAuth application requests `identify guilds.members.read`. The configured application client ID, client secret, guild ID, database URL, and a stable `NEXTAUTH_SECRET` stay in `apps/web/.env.local`. A bot token is not required for this login flow.

## Authorization response issuer

The Discord provider explicitly sets `issuer: https://discord.com`, matching the [official authorization-server metadata](https://discord.com/.well-known/openid-configuration). Discord may return an `iss` query parameter in the authorization response. NextAuth4's built-in provider omitted its expected issuer, so the installed OAuth client rejected those callbacks before token exchange. The expected issuer is a trusted constant, never learned from callback input. Existing state-cookie validation, scopes, code exchange, `/users/@me` profile retrieval and Guild membership authorization remain unchanged. ID-token mode is not enabled. Regression tests use the actual installed provider normalization and OAuth callback client with synthetic grants; foreign issuers, wrong/missing state and missing signed state cookies still fail before exchange.

## Token custody

- `accounts.access_token` and `accounts.refresh_token` contain versioned AES-256-GCM ciphertext, never plaintext. HKDF-SHA-256 derives a separate encryption key from the stable authentication secret; authenticated additional data binds each envelope to the Discord account ID and access/refresh column. Each write uses a fresh random 96-bit nonce.
- The authentication secret must contain at least 32 characters. Blank or short secrets cannot persist live OAuth tokens. Changing this secret invalidates sessions and makes earlier token envelopes unreadable; those users must sign in again. This implementation does not provide an automatic key rotation migration.
- OAuth access, refresh and ID tokens are never stored in the JWT, returned by the session callback, sent to the browser, or included in audit metadata. Unauthenticated legacy plaintext account values are rejected.
- Scopes and expiry are stored as non-secret account metadata. Account rows and user history remain intact when credentials are cleared.

## Internal permissions and Discord verification

`apps/web/src/lib/server/discord-authorization.ts` exports:

```ts
getLiveGuildEligibility(userId: string): Promise<
  "MEMBER" | "LEFT" | "UNAVAILABLE" | "REAUTH_REQUIRED"
>
getLiveGuildEligibilityState(userId: string): Promise<{
  status: "MEMBER" | "LEFT" | "UNAVAILABLE" | "REAUTH_REQUIRED";
  retryAfterSeconds: number | null;
}>
getSessionGuildEligibilityState(userId: string): Promise<{
  status: "MEMBER" | "LEFT" | "UNAVAILABLE" | "REAUTH_REQUIRED";
  retryAfterSeconds: number | null;
}>
```

The session callback validates the signed identity and reads its current database user without calling Discord. `getCurrentSessionState()` exposes this identity only for the account/navigation display. It must never authorize a protected read or mutation. Protected page reads and writes use `getCurrentAuthState()` or `getCurrentUser()`: these require the signed session, a current linked Discord account with the required consent scope and a readable, correctly bound encrypted access-token envelope, and the user's current internal database role. Missing or cleared credentials, reduced stored scopes and unreadable envelopes require sign-in again.

`getSessionGuildEligibilityState()` retains its compatibility name but performs these local database/credential checks only. Its `MEMBER` result means the persisted login grant remains acceptable locally; it is not a new Discord membership confirmation. Normal requests do not check Discord token expiry, refresh tokens or call the Discord membership API. An expired Discord access token alone does not invalidate a still-valid site session. Discord rate limits, outages and transport cooldowns therefore do not block normal pages or writes merely because Discord cannot be reached. Database and local credential checks still fail closed. Existing development mock identities continue to use their restricted development-only policy.

The authentication options resolve the configured signing secret when used instead of retaining an earlier development fallback after an environment reload. React `cache` and request-owned header object WeakMaps share repeated session/authorization reads inside the same HTTP request, including its action and response render. A later request checks the current grant and database role again. Roles from the JWT, browser or previous request do not authorize access. Mutation repositories also re-read actor and target roles in their own database transactions, so internal approval withdrawal and role changes take effect on the next authorized request. The former five-minute process-memory membership snapshot and sign-in priming are no longer part of normal authorization.

Discord sign-in still checks the configured Guild membership and matches the returned Discord user ID before persisting the identity. Before the remote check, it captures any existing linked account's encrypted credential generation. A confirmed nonmember is refused a new login; if that captured generation is still current, the callback also demotes the linked user to `GUEST`, clears credentials and records the confirmed departure. A mismatched identity or unavailable check refuses the new login without changing the stored account. `getLiveGuildEligibilityState()` and the string `getLiveGuildEligibility()` perform a fresh Discord membership check for explicit verification, including checking a target before approving or changing membership roles. These live operations can require token refresh and can be blocked by Discord downtime or rate limits. Their results are applied only to the checked account's still-current credential generation; an older response cannot revoke a newer sign-in grant.

`getCurrentAuthState()` returns `{ user, status, retryAfterSeconds? }`, where status is `GUEST`, `AUTHENTICATED`, `REAUTH_REQUIRED`, `UNAVAILABLE`, or `LEFT`. Only an absent session without an existing session cookie is an anonymous `GUEST`; an unreadable existing cookie is `REAUTH_REQUIRED`. A blocked signed-in session never becomes anonymous demo data. The session callback recomputes the safe identity `authStatus` on the server, ignoring any JWT status marker. The authorized reader omits the user for blocked states. Database failures during local account or final role reads produce `UNAVAILABLE`; `getCurrentUser()` returns `null` while the richer helper retains the reason for the HOME/SEASON provider. A locally accepted identity whose current database role is `GUEST` remains `AUTHENTICATED` and is subject to that role's usual permissions.

## Browser login continuity

JWT and session cookies have the same seven-day lifetime. `SessionKeeper` makes a same-origin, uncached `GET /api/auth/session` on mount, every 15 minutes, and when the tab becomes visible/focused (with a shared 30-second throttle). This endpoint renews the HTTP-only cookie without a Discord membership call. Server-component session reads alone cannot renew browser cookies. The client never treats returned roles as permission, stores login information in browser storage, or signs out after a network failure. Explicit logout first synchronously cancels pending renewals, timers and listeners; a same-origin BroadcastChannel sends only `STOP_RENEWAL` to other active tabs. This prevents a late renewal from restoring a cookie that sign-out just cleared. The logout flow also works without BroadcastChannel support.

Logout ends the local site login only. It does not call Discord, revoke the external OAuth grant or clear the persisted Discord credentials. Signing in again performs the usual live sign-in membership check. Normal session renewal and logout do not depend on Discord availability.

Automatic navigation prefetch remains disabled on the main menus and protected season/admin links. Discord `Retry-After` and exhausted bucket reset headers establish process-local transport cooldowns keyed by token hash/route for sign-in and explicit live checks. A blocked live check returns only the safe retry delay and preserves recoverable OAuth credentials, account identity and roles. That cooldown does not affect the local authorization of normal pages or writes.

Admin guards use the richer local authorization state. `UNAVAILABLE`, including a database failure, raises a controlled, token-free authorization error and offers a retry in the current admin flow instead of redirecting a signed-in operator to login. Anonymous, re-consent and confirmed-leave states still redirect with their appropriate existing login messages. Admin error recovery uses Next.js `retry()` to re-fetch authorization. A target approval's explicit Discord check remains a separate required step and may fail while the operator's own session remains authorized.

Internal database role changes are observed on the next authorized request. External Discord Guild departure or revoked OAuth authorization is detected at the next sign-in or explicit live check, not within a five-minute window and not during ordinary page reads or writes. Until such a check, an otherwise valid existing site session can continue using its current internal role and locally accepted grant. There is no Discord bot, gateway listener, scheduled poll or background revocation guarantee. A process restart does not require Discord to reauthorize every existing session.

## Expiry, refresh and races

Expiry and refresh apply only when a live Discord operation needs a usable access token. Tokens within 30 seconds of expiry, and tokens with unknown expiry, require a refresh before that live check. Normal site authorization ignores Discord access-token expiry and does not attempt refresh. An account row lock surrounds the refresh read/exchange/write transaction, serializing refresh-token rotation across application processes. Both rotated tokens are encrypted before committing; the old expired access token is never used as a live-check fallback after a failed refresh. Discord outage during refresh denies that live operation without discarding recoverable credentials. Rejected/revoked refresh grants and reduced consent scopes clear credentials and require new consent.

The membership API call runs without holding a user-role or global membership lock. A confirmed leave subsequently takes advisory transaction lock `912743110`, locks the user and account, and compares the checked encrypted token to the current row. For sign-in, this comparison uses the existing grant captured before the remote membership check. A newer sign-in or refresh invalidates an old leave response instead of letting it overwrite a newer identity state. This lock is shared by member approvals and the first-admin bootstrap.

The sign-in race guard also captures the PostgreSQL account-row version, `xmin::text`, alongside the encrypted grant. Both must still match before confirmed-absence cleanup. Even a transition from cleared credentials to a new token and back to cleared credentials changes the row version, so it cannot match an older pending sign-in check. This row-version proof exists only for that pending check's lifetime; it is not stored as application metadata and requires no schema migration.

An explicit live membership request rejected as unauthorized also clears credentials only if the checked account and encrypted access-token generation are still current. It does not change the internal role, because a revoked grant is not evidence that the user left the Guild. The next normal request sees the cleared local credentials and requires sign-in again. A stale unauthorized response cannot clear a newer grant.

After a confirmed leave, another successful guild sign-in changes `GUEST` to `APPLICANT`. Previous privileged roles are not restored, and membership approval is required again. Existing profile, season, operation and build records are retained.

Approval actions should require `getLiveGuildEligibility(targetUserId) === "MEMBER"` before starting their role-change transaction, then re-read actor and target roles under their own locks. Do not call the helper while holding the shared advisory lock: a confirmed leave needs its own lock-owning transaction.

## Verification scope

Regression coverage includes authenticated-encryption tampering and account/column binding, local per-request grant and role checks, normal authorization with expired Discord access tokens and unavailable Discord transport, and the absence of membership/refresh calls on normal reads and writes. Live-operation coverage includes mocked HTTP response classification, serialized refresh rotation, forced-live approval checks, outage denial for that live operation, confirmed-leave clearing/demotion at sign-in and explicit verification, reduced consent, explicit unauthorized-grant clearing without false departure, and rejection of superseded credential responses. Transport and lifecycle tests use synthetic credentials; they do not log in as a real Discord user or remove anyone from the real Guild. Actual account consent remains a user-driven browser step.
