# 시즌·작전 등록 관리 검증

검증일: 2026-10-06. 시즌 등록 승인·직접 참여에 더해 시나리오 고정 단계, 관리자 이전·다음 진행과 개별 시즌 상세를 구현했습니다. 기존 Docker PostgreSQL에 0001_season_participation.sql과 0002_manual_season_phases.sql을 적용했으며 기존 사용자·서버 자료는 유지합니다.

## 구현 범위

- `/admin/seasons`: 서버 주소와 시즌 번호 통합 입력, 하이브 이름·선택 정산일·시즌 정보 수정, 신청 승인·반려, 참가자 추가·상태 수정·명단 삭제, 고정 단계 자동 구성과 관리자 이전·다음 진행, 투표 설정.
- `/season`: 승인된 시즌 목록과 직접 참여. `/season/[id]`는 선택한 시즌의 단계·참가·마지막 단계 이동 신청입니다. `/season/new`와 `/season/requests/[id]`는 일반 멤버의 등록 신청과 본인 신청 수정입니다.
- 시즌은 계획 → 진행 → 정산 → 보관 순서이며 HOME의 현재 시즌은 하나입니다. 단계는 날짜가 아닌 저장된 순서로 판단합니다. 단계 변경은 전체 시즌 상태를 바꾸지 않습니다. 예정 작전은 완료·취소한 뒤 정산합니다.
- `/admin/operations`: 작전 생성·수정·완료·취소, 정원과 참가 응답 확인. 완료·취소 후 편집하지 않으며 기존 역할과 응답을 보존합니다.
- `/ops`, `/ops/[id]`: 승인 멤버의 전체 작전 목록, 브리핑, 참가 응답. 탈퇴자의 예약은 정원에 포함하지만 공개 명단에서는 제외합니다.
- 입력 시각은 KST이며 서버에서 ISO UTC로 변환합니다. 변경하지 않은 기존 기록은 초·밀리초 정밀도를 유지합니다.

## 고정 단계·수동 진행

네 시나리오는 비정상수용 3단계(사용자 지정), 땃쥐 일반 5단계, 설산 개편 4단계, 무한의 꿈 6단계를 자동 구성합니다. ADMIN만 승인된 비보관 시즌의 현재 순서를 변경하며 범위 초과·중복 제출·오래된 버전·OFFICER의 변경을 거부합니다. 시나리오 수정 시 1단계로 초기화하고 이전 단계 명칭·날짜·초과 행을 역사 자료로 보존합니다. 현재 화면·작전·투표·이동 신청에는 선택한 시나리오의 유효 단계만 사용합니다.

통합 검사는 날짜가 없는 단계의 활성화, 마지막 단계의 승인된 PLANNED 시즌 이동 신청, 이전 단계로 되돌린 뒤 READY·투표 보존, 같은 시즌의 재진입, 승인 대기 공개 제한 및 서로 다른 시즌 데이터의 분리를 확인합니다. 추가 검토에서 멤버 이동 상태 저장의 수정 버전이 같은 밀리초에 재사용될 수 있음을 확인해 항상 증가하도록 수정했습니다. 미래 버전에서도 증가하고 이전 버전의 관리자 수정은 충돌로 거부하는 PostgreSQL 회귀 검사가 통과했습니다. `pnpm db:verify`의 기본값·양수 단계 제약을 포함한 29개 검사는 전체 rollback으로 끝납니다.

Chrome의 실제 ADMIN 계정으로 임시 무한의 꿈 시즌을 만들었습니다. 수동 단계 입력 없이 여섯 단계가 저장되고, 참여·1→6 진행·마지막 단계의 READY 저장·6→5 복귀를 확인했습니다. 이전 단계에서는 신청 폼이 숨겨지고 같은 참가자의 READY 기록은 DB에 유지됐습니다. 기존 UNIZ 시즌은 단계가 없던 기록에 여섯 단계가 자동 보충됐고 기존 주소·시작일·참가자는 유지됐습니다. 검증용 시즌과 서버·참가·감사 기록만 자체 식별자로 정리했으며 기존 UNIZ 시즌과 계정은 보존했습니다.

연속 화면 확인 중 Discord HTTP 429 한 건을 안전한 상태 진단으로 확인했습니다. Retry-After는 261초여서 기존 8초 한도를 넘었으며, 해당 요청은 DB 쓰기 전에 UNAVAILABLE 안내로 끝났습니다. 같은 확인 과정의 다른 일곱 응답은 HTTP 200이었습니다. 제한 bucket 범위는 확정하지 못했습니다. 임시 진단은 제거했으며 토큰·응답 본문을 출력하지 않았고 요청 간 인증 캐시나 권한 완화도 추가하지 않았습니다.

새 관리 DB 테스트 9개는 실제 저장소와 SQL을 실행합니다. 외부 Discord 응답과 인증 주체만 테스트용으로 대체합니다. 생성 → 단계·후보·멤버 등록 → 활성화 → 투표·이동 상태·RSVP → 작전 종료 → 정산·보관의 흐름, 승인·역할·계정 재검증, 시간 겹침, 오래된 수정 버전, 정원 축소와 동시 참가, 이력 보존 및 UID·토큰 제외를 확인합니다. 테스트는 로컬 `uniz_hive` 연결만 허용하며 자체 생성한 UUID 자료만 정리합니다.

실제 Chrome 화면 검증 중 Discord 가입 확인 API의 HTTP 429를 확인했습니다. 서명이 깨진 것으로 추정했던 재로그인 안내를 바로잡고, 짧은 `retry_after`/`Retry-After`를 지키는 재시도와 관리자 연결 복구 화면을 추가했습니다. 동일한 8초 한도 안에서 최대 두 번 재시도하며, 긴 제한·잘못된 응답·연결 장애는 접근을 거부합니다. 인증 결과를 요청 간에 캐시하지 않습니다. 이 흐름과 관리자 오류·접근 상태는 기본 테스트로 검증합니다.

Production 브라우저용 정적 파일 27개를 로컬 Discord Secret·세션 Secret·DB URL과 비교해 어느 비밀값도 포함하지 않음을 확인했습니다. 키·토큰·UID는 검사 출력에 포함하지 않았습니다.

Chrome의 실제 ADMIN 계정으로 시나리오·서버·시즌·단계와 참가 명단을 등록하고 시즌을 활성화했습니다. 등록한 작전이 HOME 및 `/ops`에 표시되고, HOME의 Going 응답과 브리핑의 미정 변경이 실제 저장·화면 갱신되는 것을 확인했습니다. SEASON에도 등록된 시즌과 단계가 반영됐습니다. 브리핑 화면의 전체 너비는 1900px이며 가로 넘침은 없었습니다. 모바일 실계정 검증은 별도입니다.

화면 검증용으로 생성한 시나리오·서버·시즌·작전과 연결된 테스트 참가·단계·응답 및 감사 기록만 식별자로 정리했습니다. 실제 사용자 프로필, 관리자 권한과 최초 관리자 기록은 유지합니다. 화면 증빙은 Git 제외 `artifacts/cms-*-proof.jpg`에 있으며, 임시 자료는 실제 게임 운영 정보가 아닙니다.

## 시즌·서버 통합과 승인·직접 참여

이후 요청으로 시즌 번호와 서버 주소 입력을 하나로 합쳤습니다. 정산일은 기본 폼에서 숨기고 선택 사항으로 저장하며, 하이브 이름은 ‘시즌에서 사용할 하이브 이름’으로 표시합니다. 서버 카탈로그 관리 화면은 제거했습니다. 신규 시즌은 운영진이면 즉시 등록하고, 일반 멤버이면 승인 대기입니다. 관리자만 검토·승인·반려할 수 있으며 멤버는 본인 신청을 수정·재신청할 수 있습니다.

승인된 준비 중·진행 중 시즌에는 멤버가 직접 참여합니다. 관리자 참가자 추가·상태 수정·명단 삭제를 제공하고, 삭제된 참가자를 인원·명단·투표·운영 변경 대상에서 제외합니다. 기존 투표 참조와 최초 참여일은 보존합니다. 시즌 정보는 참가 기록이 있어도 공통 수정 폼으로 변경하며, 보관 상태의 정보 수정도 지원합니다.

화면 검증 과정에서 시간 입력이 React의 변경 상태에 바로 반영되지 않는 경우를 확인해 input 이벤트도 반영하도록 보완했습니다. 실제 임시 시즌의 09:30 KST 저장·다시 불러오기로 확인했습니다. 저장과 재렌더에서 같은 Discord 확인이 반복되는 문제도 확인해 Next 요청 소유 headers 객체를 키로 하는 WeakMap을 사용했습니다. 인증 결과는 같은 HTTP 요청에서만 공유하며 다음 요청의 Guild 가입·DB 역할을 다시 확인합니다. 새 요청에서 탈퇴·장애·역할 변경을 확인하는 테스트를 추가했습니다. 일시적 연결 실패를 로그인 필요로 잘못 안내하지 않도록 구분했습니다.

이후 실제 기능 차단에 대한 사용자 피드백으로 가입 확인 방식은 변경했습니다. 현재 권한·계정 상태는 매 요청 DB에서 확인하고 성공한 Discord 가입 확인만 최대 5분 재사용합니다. 이 기간을 넘겨 오류에서 재사용을 연장하지 않으며 멤버 승인 대상은 새 가입 확인을 요구합니다. 실제 시즌의 다음·이전 왕복과 새로고침 검증은 [후속 기능 차단 수정](verification-live-operations.md#후속-기능-차단-수정--2026-10-06)에 기록했습니다.

실제 Chrome의 ADMIN 계정으로 임시 시즌을 정산일 없이 만들고, 09:30 KST를 저장해 다시 불러왔습니다. 직접 참여해 인원이 1명이 되는 것, 관리자의 준비 상태 수정, 참가자가 있는 시즌의 하이브 이름·주소 수정, 명단 삭제 후 0명 표시를 확인했습니다. 승인 대기 신청 fixture는 승인 전 일반 목록에 없었으며, 관리자 승인 후 참여 버튼과 함께 공개됐습니다. 일반 MEMBER의 실제 OAuth 화면은 별도 계정으로 확인하지 않았으며 신청자 권한·본인 신청·반려·재신청은 PostgreSQL 통합 검사로 확인했습니다.

화면 검증용 시즌 2개·서버 3개·신청자와 해당 참가·감사 기록만 자체 식별자로 정리했습니다. 실제 관리자·프로필과 기존 `E_Dream-X0070 · 한국`은 보존합니다. 증빙은 `artifacts/season-evolution-editor.png`, `artifacts/season-evolution-participation.png`, `artifacts/season-evolution-management.png`입니다.

2026-10-06 폼 통일 요청으로 시즌 관리와 새 시즌 만들기는 같은 생성 폼을 사용합니다. 실제 등록된 `E_Dream-X0070`의 시나리오·번호·한국 지역이 두 화면에 동일하게 표시됩니다. 두 화면에 시즌 시작·정산 달력이 있으며 실제 Chrome에서 10월 8일 선택, 09:30 시간 변경, 다음 달 이동 및 11월 8일 선택을 확인했습니다. 확인용 날짜는 저장하지 않고 초기화했습니다. 추가 기본 검사 21개는 공유 선택과 입력 경계를, DB 검사 5개는 네 가지 생성·기존 서버 재사용·지역 보존·날짜/중복 실패의 전체 rollback·최신 권한 검증을 확인합니다. 기존 사용자 서버와 프로필은 유지했으며 새 시즌은 만들지 않았습니다. 증빙은 `artifacts/season-unified-management.png`와 `artifacts/season-unified-new.png`입니다.
