# Build Planner V2와 기존 V1 기록

2026-10-09. 신규 빌드는 `uniz-gear.v2`의 슬롯 기반 장비 화면을 사용한다. 기존 `uniz-planner.v1` 구성과 편집 화면은 유지하며 자동 변환하지 않는다. 두 형식 모두 `builds`와 `build_versions`에 저장한다. 공유 승인·본문 이미지·좋아요는 migration0008의 별도 테이블에 기록한다.

## 화면과 흐름

- `/lab`: 내 빌드, 하이브 공유, 공개 빌드를 각각 9개씩 조회한다. 내 목록은 최신 초안, 공유 목록은 현재 승인 버전의 이름·설명·추천 콘텐츠·태그·추천 메모만 검색한다.
- 내 빌드 기본 목록에는 보관하지 않은 기록만 표시한다. `/lab?archived=1`의 보관함에는 본인이 보관한 빌드를 9개씩 표시하며 검색·페이지 이동 시 보관함 상태를 유지한다. 보관한 기록은 상세 화면에서 기존 보관 해제 기능으로 복원할 수 있다. 잘못되거나 반복된 `archived` URL 값은 기본 목록으로 처리하고, 하이브·공개 목록의 승인·보관 제외 조건은 바꾸지 않는다.
- `/lab/new`: 주·보조·근접 무기, 방어구 6부위, 전투 감염물, 크래들 8칸에서 장비를 선택한다. 기본 공개 범위는 `PRIVATE`다.
- `/lab/b/[id]?version=N`: 특정 버전의 장착 구성표·조건·메모를 읽고 구성표를 복사한다. 버전 없는 URL은 작성자에게 최신 초안, 다른 사용자에게 현재 승인 버전을 연다. 미승인 버전은 작성자만 읽는다.
- `/lab/b/[id]/edit?from=N`: 선택한 과거 구성의 형식을 유지해 새 버전을 시작한다. 저장하면 최신 번호 다음에 추가하며 과거 구성은 바꾸지 않는다.

V2는 게임 장비창처럼 슬롯·선택 모달·상세 패널을 사용한다. 빈 슬롯은 검색 입력을 열고, 등록된 슬롯은 상세·모듈 설정만 선택한다. 등록 장비의 검색은 명시적 장비 변경 버튼으로만 연다. 이름·별칭을 입력하면 아이콘과 함께 최대12개 자동완성 결과를 표시한다. 결과를 누르거나 방향키·Enter로 바로 장착하고, 전체 결과는48개씩 탐색한다. 한글 음절 조합 중에도160ms 뒤 결과를 갱신하지만 조합 확정 Enter와 조합 종료 직후75ms Enter는 장착하지 않는다. 첫 Esc는 검색 목록, 다음 Esc는 선택창을 닫고 원래 슬롯으로 초점을 돌린다. 검색은 브라우저 내부의 부위별 후보만 처리하고 DB/API 요청을 보내지 않는다. 이미지도 표시하는 항목만 지연 로딩한다. 3D 렌더링은 없다.

무기에는 총구·사이트·전술·탄창·탄약·신판 모듈을 연결한다. 신판 모듈은 일반·섬광과 접미사를 포함한 변형 이름·아이콘으로 선택하고 장비 부위를 필터한다. 모듈 레벨은 입력하지 않으며 새 선택은 `null`이다. 기존 저장의 레벨·접미사는 동일 모듈을 유지하면 보존하고 교체·해제하면 초기화한다. 최고 보유 레벨을 알 수 없으므로 임의로17을 기록하지 않는다. 전투 감염물의 능력·활동 등급·특성, 추천도1~5·콘텐츠·태그는 별도 기록이다.

2026-10-08 근접 모듈 호환 분류를 보정했다. 신판 일반 무기 모듈368변형(일반184/섬광184)은 근접 무기18개에서도 선택·저장할 수 있고 목록에 ‘원거리·근접 무기’로 표시한다. 모듈 `apply_list`는 `item_data.sub_type`과 연결하며 장비 `equip_data.arm_type`과 구분한다. 원본 `ModDataHelper.check_mod_can_equip_v2`의 정적 검사도 `sub_type in apply_list`를 사용한다. 근접은 전자10/후자9이고, 대형 무기 subtype8은 RPG7·유탄 발사기·화염 방사기의 서로 다른 장비 계열을 포함한다. 무기 모듈에 연결된 접미사14개만 근접 허용 부위에 포함하며 방어구 전용 모듈·접미사, 탄약·조준경 등의 부위 제한은 유지한다. 기존 저장 ID·일반/섬광 구분·아이콘·레벨 기록 정책은 그대로다.

게임 버전·시나리오·PVE/PVP·PC/모바일·클래스와 모르는 숫자는 비워 둘 수 있다. 저장 실패 시 입력과 숫자 오류를 유지한다. 성공 후 중복 제출을 막고 저장한 버전 상세로 이동한다. 입력은 저장 전까지 컴포넌트에만 있으며 별도 클라우드 초안은 없다.

보관은 전체 공유와 대기 중인 신청을 중단하며 작성자의 이전 버전을 남긴다. 복원하면 나만 보기로 돌아오며 공유에는 다시 승인이 필요하다. 장비 구성·제목·설명·본문·영상·조건·추천 기록·버전 메모는 버전별로 보존한다.

## 공유 승인과 관리자 추천도

PRIVATE 빌드는 개수 제한 없이 저장한다. 입력 크기·사진 수·멤버 권한 조건은 유지한다. HIVE/PUBLIC으로 저장하거나 공유 설정을 바꾸면 정확한 버전의 공유 신청을 만든다. ADMIN만 `/admin/builds`에서 신청한 버전과 당시 제목·설명·범위를 검토해 승인·반려한다. OFFICER는 승인할 수 없다. 관리자도 제출되지 않은 타인의 비공개 버전은 읽거나 수정하지 못한다.

승인된 v1이 공유 중일 때 PRIVATE v2를 저장하면 v1은 계속 공유된다. v2 공유를 신청해도 승인 전까지 v1이 유지되며 반려해도 기존 공유를 바꾸지 않는다. 명시적으로 공유 중단을 선택하면 현재 공개와 모든 과거 승인 링크를 숨기고 대기 중인 신청을 취소한다. 새 신청은 같은 빌드의 기존 대기 신청을 취소한다.

과거 승인 버전의 고정 링크와 커뮤니티 첨부는 현재 공유가 활성화된 동안 보존한다. 현재 공유 범위와 과거 승인 범위를 모두 만족해야 하며, 미승인 버전은 버전 목록과 첨부 후보에 넣지 않는다. 관리자가 한 버전의 승인을 해제하면 같은 버전의 반복 승인 요청도 해제해 우회 노출을 막는다. 그 버전이 현재 공유 중이면 전체 공유를 중단한다.

관리자 추천도는 선택 사항인1~5점과500자 평가다. 승인 버전에 표시하며 작성자가 장비 구성에 기록한 개인 추천도와 구분한다. 검토 의견은1000자까지 작성자와 관리자에게만 표시한다. 신청 당시 제목·설명·버전·공유 범위는 DB trigger로 고정한다. 현재 관리자 역할·Discord 연결과 공유 authorization gate를 확인하고 빌드→신청 순서로 잠근 뒤 승인 상태·공개 포인터·감사 기록을 함께 저장한다. `expectedUpdatedAt`이 다르면 다시 검토해야 한다.

본문은 검증된 `uniz-content.v1` 문서와 검색용 설명을 별도 저장하며 장비 snapshot에 섞지 않는다. 문서256KiB·이미지10개·설명5000자 제한을 적용한다. 사진 참조는 본인 소유만 새 버전에 연결하며 이미지 연결 실패 시 빌드 저장도 함께 취소한다. YouTube 링크는 정해진 도메인과 영상 ID로 정규화한다. 승인된 공유 빌드의 좋아요는 현재 승인된 실제 멤버만 변경하고 방문자는 PUBLIC 집계만 읽는다.

## V2 장비 목록과 검증 범위

`packages/build-engine/src/model/gear-catalog.json`은 공식 자료·사용자 게임 캡처·개별 커뮤니티 자료로 이름과 부위, 확인 가능한 연결 관계를 대조한 항목만 선별한다. 현재 게임의 전체 장비 목록이나 모든 패치·시나리오의 능력치를 완성한 데이터는 아니다. 실재 여부·장착 부위·연결 근거가 없는 항목을 임의로 만들지 않는다. 확인되지 않은 수치·아이콘·희귀도는 `null`로 남기고 계산에 사용하지 않는다.

2026-10-07 확장·보완 후 총2127기록이다. 신규 선택에는 무기85·방어구181·신판 모듈1662변형(일반831/섬광831)·전투 감염물23·현대 크래들25개를 제공한다. 공개 설계도 ID와 로컬 Steam build25590224의 원본 장비·아이템·모듈 범위·한국어 번역을 연결했다. 제작단계 복제·NPC·디버그 등 원시 장비7709행을 직접 선택지로 넣지 않는다. 특성110개 중 기존62개를 보존하고 일반 후보48개를 추가했다. 명시적 외형 연결·사용자 캡처와 DeviationHelper의 COMMON/type별 선택, 본체 quality_dict, 양수 가중치 drop pool을 대조한 관계만 허용한다. 현대 시즌 서버 전용 융합 풀은 클라이언트에 없어 전체 현재 획득 가능 범위로 확대하지 않는다. 액티브 스킬258개를 패시브 특성으로 넣지 않는다.

울프·세이버 장비는 displayName을 우선 표시하며 원본 name과 과거 snapshot은 유지한다. 울프/고독한 늑대/늑대, 세이버/구원자 등은 같은 ID를 검색한다.24개 세트의 원본 이름과94개 실제 임계값 효과를 표시한다. 현재 착용 수에 도달한 효과만 활성 표시하고 수치를 합산하지 않는다. 핵심 방어구는 equip_origin_data.suit_type=3과 EQUIP_SUIT_GOLDEN_TYPE 상수·실제 UI 장착 검사 관계로39개를 분류했다(세트137/일반5). 둘째 핵심은 선택·새 저장에서 막고 기존 장비를 자동 삭제하지 않는다. 역사적 버전의 읽기는 그대로다.

감염물 특성은 실시간 다중 선택 검색과 선택된 칩·해제로 기록한다. 결과는12개씩 탐색하고 페이지 버튼·PageUp/PageDown으로 다음 후보를 연다. 저주 인형은 외형2개와 확인된 일반 후보를 포함해51개가 제공된다. 크래들25개에는 게임 UI의 entry desc 또는 정확한 buff_level_data [buffID,1] 및 desc_value 치환으로 확보한 한국어 효과를 표시하고 구성표 복사에도 포함한다.

기존29개 저장 ID는 유지한다. `legacyOnly` 항목은 새 선택 목록에서만 숨기고 기존 저장 검증에는 남긴다. 전투 나비를 영지형 Rebecca인 ‘나비의 꿈’으로 잘못 표기했던 오류는 `correctedNames`로 화면·복사에서만 정정하고 snapshot JSON은 변경하지 않는다. 다른 과거 이름은 계속 보존한다. 잘못된 이름은 검색 별칭에도 넣지 않는다.

343개 원본 아이콘의 공개 파일·RGBA·출처·해시 연결을 검증했다. 모듈32개는 접미사 계열의 공유 문양이며 특성3개도 분류 공유 문양으로 표시한다. 게임 파일 추출은 개발 중 오프라인으로만 수행하며 페이지 요청이나 검색 때 실행하지 않는다. 원본 연결 기록은 `packages/build-engine/data/expanded-gear-asset-provenance.json`과 기존 manifest에 있다.

`PlannerGearLoadout`, `gearLoadoutSchema`, `parseGearLoadoutForSave`는 V2 신규 저장 경계다. `parseGearLoadout`과 역사적 구조 읽기는 기존 호환성을 유지한다. 신규 저장은 핵심 방어구 최대1개를 추가로 확인하며 슬롯별 장비 종류와 ID, 부속품 위치와 무기 계열, 신규 모듈 여부, 허용한 접미사·개체 특성을 검사한다. 비어 있는 부속품 호환 계열은 전체 호환으로 취급하지 않는다. 특정 장비로 확인한 `compatibleItemIds`가 있으면 그 목록이 계열 규칙보다 우선한다. 예를 들어 P90 캡처에서 확인한 중구경 철갑탄을 모든 기관단총에 확장하지 않는다. 알려진 시나리오 제한이 있으면 선택한 시나리오와 일치해야 한다.

크래들의 현재 시나리오별 가용 여부와 캐릭터 해금 조건은 미확인이다. `scenarioKeys: []`인 항목은 사용자의 구성 기록으로 선택·저장할 수 있으며 모든 시나리오에서 사용할 수 있다는 보증이 아니다. 8칸은 제공된 화면을 따른 기록 위치이고 전역 해금 규칙이나 모든 모드의 슬롯 수를 확정한 것이 아니다. 이 제한은 편집기·선택 상세·저장 구성표와 복사 결과에서 안내한다. 게임에서 실제 사용 가능 여부를 확인해야 한다.

V2는 각 슬롯을 한 번만 사용하고 같은 크래들의 중복 선택을 거부한다. 모듈을 해제·교체하면 접미사와 레벨도 초기화한다. 모듈 없는 접미사·레벨, 감염물 이외의 개체 등급·특성, 감염물·크래들의 장비 부속품은 허용하지 않는다. 서로 다른 슬롯에 같은 무기를 기록하는 것은 미확인 게임 규칙을 추정해 막지 않는다.

V2 숫자는 `null` 또는 유한한 양의 정수다. 장비·개체 레벨과 등급은 1~100의 저장 한계, 모듈 레벨은 확인된 1~17 범위를 사용하며 1~100을 게임의 최대 등급이라고 주장하지 않는다. 추천 콘텐츠는 16개, 태그는 24개까지 받고 공백·해시 기호·중복을 정리한다. 전체 요청은 UTF-8 512KiB 이내이며 알 수 없는 필드, UID·역할·owner·계산 수치는 입력으로 받지 않는다.

모듈 범위의 근거는 [공식 한국어 신규 모듈 FAQ](https://www.oncehuman.game/kr/news/devBlog/20260123/40777_1283433.html)의 1~17레벨 표와 [공식 개편 설명](https://www.oncehuman.game/news/devBlog/20251212/40781_1276354.html)의 최대 Lv.17 표기다. 이후 범위가 바뀌면 이 저장 계약도 근거와 함께 갱신한다.

새 저장의 `catalogNames`는 클라이언트 이름을 신뢰하지 않고 선택한 ID의 현재 목록 이름으로 다시 만든다. 과거 기록은 당시 이름을 우선 표시한다. 삭제·수정된 목록 항목의 과거 ID는 구조를 검증해 읽을 수 있으나 다시 저장할 때는 현재 선택 기준을 만족해야 한다. 자료에 표시된 기본 옵션을 사용자가 기록한 레벨에 맞춰 자동 보간하거나 합산하지 않는다.

## 음식·음료 도핑

V2의 선택 사항인 `consumables`에는 `foodIds`, `drinkIds`, `notes`를 기록한다. 장비 슬롯과 기존 ID는 바꾸지 않으며 이 필드가 없는 과거 V2도 계속 읽을 수 있다. 셰프(한국어 `셰프` 또는 대소문자를 구분하지 않는 `Chef`)는 서로 다른 음식 2개와 음료 2개, 나머지 직업·미기록은 음식 1개와 음료 1개를 선택한다. 각 종류의 한도는 독립적이며 남은 음료 칸을 음식으로 사용할 수 없다. 같은 품목의 중복 선택, 잘못된 종류, 알 수 없는 ID는 새 저장에서 거부한다. 셰프에서 다른 직업으로 변경해도 기존 선택은 삭제하지 않고 초과 항목을 해제하도록 안내한다.

`packages/build-engine/data/consumables-catalog.json`은 한국어 이름, 검색 별칭, 원본 아이콘, 기본 효과 수치·지속 시간·조건, 필수·선택 제작 재료를 제공한다. 자료의 기본 수치에 선택 재료나 셰프 제작 강화를 자동 합산하지 않는다. 실제 제작 조건은 2,000자 도핑 메모로 기록할 수 있다. 셰프의 음식 2개·음료 2개 규칙은 [2026년 5월 공식 공지](https://www.oncehuman.game/kr/banner/20260513/41909_1300133.html)와 대조했다.

30개 후보는 음식 19개와 음료 11개다. `cuisine_common_data.cuisine_type`과 실제 사용 버프의 배타 태그(음식 2, 음료 3)를 연결해 분류한다. 버프 설명의 `buff_type` 문자열만으로 분류하지 않는다. 스타더스트 버섯 수프와 훈제고기 보르시는 음료이며, 찌릿찌릿 호박죽은 음식이다. 후자는 [2026년 8월 공식 수정 공지](https://www.oncehuman.game/kr/news/update/20260824/40776_1312017.html)와도 일치한다.

제작 재료는 `forge_data`와 `forge_choice_material_data`의 정확한 ID로 연결한다. 서로 다른 원본 제작표에 재료 차이가 있으면 별도 재료 조합으로 표시하고 현재 시나리오의 기본값으로 추정하지 않는다. 선택 재료마다 수량이 다를 수 있어 개별 이름·수량을 보존한다. 제작표의 내부 키를 제품 화면에 노출하지 않는다. 불완전한 숫자·설명은 미확인 표시를 유지한다.

30개 아이콘은 기존 장비와 같은 오프라인 추출 방식으로 제공하며 해시·투명도·PNG 왕복 검증 기록은 `consumables-asset-provenance.json`에 보존한다. 요청 시 추출하거나 DB에 이미지 바이트를 저장하지 않는다. 빌드에는 선택 ID·신뢰한 이름·메모만 저장하고 상세 구성표·복사에도 도핑을 포함한다. 과거 버전과 기존 공유 승인 정책은 유지한다.

## 기존 V1 보존

`PlannerLoadout`, `plannerLoadoutSchema`, `parsePlannerLoadout`의 `uniz-planner.v1` 계약은 유지한다. 이름·장착 위치·티어·별·보정·레벨·부옵션을 직접 기록하고 같은 구성 안의 장비를 연결한다. 역사적 공식 근거 21개 중 개별 ITEM 12개만 참고 선택지로 사용하며 SET·SYSTEM·TARGET·EFFECT는 제외한다. 새 저장은 참고 ID·SHA-256 revision·분류·이름을 확인하고, 과거 읽기는 당시 reference를 보존한다. 현재 패치 적용과 사용자가 입력한 게임 수치는 미확인이다.

V1은 빈 숫자 `null`과 명시한 0을 구분한다. 최대 항목 64개, 항목별 부옵션 32개, 정수 0~1,000,000, 유한한 부옵션 값 ±1,000,000,000을 허용한다. UUID 대소문자를 정규화하고 중복 ID·자기 연결·없는 항목·순환 연결·알 수 없는 필드를 거부한다. 이 저장 한계를 게임 규칙으로 취급하지 않는다.

`parseVersionedPlannerSnapshot(schemaVersion, input)`은 V1·V2 구조를 구분해 읽는다. 지원하지 않는 형식이나 손상된 snapshot은 원본을 보존하고 안전한 안내를 표시한다. raw JSON을 클라이언트에 보내거나 기존 저장본을 덮어쓰지 않는다. 엔진 계약은 브라우저에서도 사용할 수 있는 순수 TypeScript/Zod이며 React·Next.js·DB·파일 시스템·네트워크에 의존하지 않는다.

## 권한·저장·조회

실제 Discord 계정과 프로필이 연결된 승인 `MEMBER`·`OFFICER`·`ADMIN`만 빌드를 만들고 본인 기록을 변경할 수 있다. 서버가 현재 인증 상태와 실제 DB 역할·계정·프로필을 검사한다. 개발 계정은 입력 미리보기만 제공한다. `UNAVAILABLE`은 로그아웃과 구분하고 저장하지 않는다.

| 공개 범위 | 읽기                                           |
| --------- | ---------------------------------------------- |
| PRIVATE   | 승인된 작성자                                  |
| HIVE      | 관리자 승인 버전을 승인된 하이브 멤버에게 공유 |
| PUBLIC    | 관리자 승인 버전을 방문자 포함 공유            |
| 보관됨    | 공개 범위와 관계없이 승인된 작성자             |

운영진 권한은 다른 작성자의 PRIVATE 빌드를 읽거나 수정할 권한을 추가하지 않는다. 현재 작성자도 승인 상태여야 목록·상세에 노출된다. DB 역할은 읽기와 쓰기에서 다시 확인하고 UID·token·원시 OAuth 계정 정보는 DTO에 넣지 않는다.

쓰기는 공유 authorization advisory gate → 사용자 공유 잠금 → 해당 Build 행의 수정 잠금 순서다. 기존 역할·프로필·가입 상태 변경은 같은 gate의 배타 잠금을 사용해 저장 중의 권한 변경을 조정한다. 다른 빌드를 저장할 때 전체 Build 목록을 잠그지 않는다. `expectedUpdatedAt`이 다르면 충돌을 안내한다. 서버 시각과 이전 시각+1ms 중 큰 값을 사용해 같은 밀리초의 변경도 구분한다. Build 메타데이터 갱신·`max(version)+1` snapshot 삽입·감사 기록은 함께 커밋한다. 기존 immutable trigger와 `(build_id, version)` unique constraint를 유지한다.

목록은 repeatable-read transaction에서 현재 승인 역할·Discord 계정과 승인 공개 범위를 필터하고 `(updatedAt, id)` 역순의 keyset cursor로 페이지를 조회한다. 내 목록은 빌드 수정일, 공유 목록은 공개 포인터 갱신일을 사용한다. 각 그룹은9개와 다음 페이지 판단용1개를 조회한다. 장비 snapshot 전체를 목록 응답에 넣지 않고 공유 검색에 미승인 초안을 사용하지 않는다. 상세는 선택한 snapshot 하나와20개 버전 메타데이터를 읽으며 다른 사용자에게는 승인된 버전만 반환한다. 과거 승인 버전이 현재 버전 목록 페이지 밖에 있어도 권한이 유지되면 읽을 수 있다.

검증 결과는 [Planner 검증 기록](verification-build-planner.md)에 있다. Static Stats·Damage Pipeline·DPS·Simulator·Compare·커뮤니티 검증은 후속 범위이며 현재 입력 기록이나 선별 목록을 계산 가능한 최신 전체 능력치로 간주하지 않는다.
